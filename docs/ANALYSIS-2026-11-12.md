# OG키보드 (og-keyboard-mac) 분석 · 버그 리포트 · 최적화 방안

- 저장소: https://github.com/ohnggni/og-keyboard-mac
- 분석 기준: `main` @ `d07f2fa` (2026-11-06), 릴리스 v0.4.0 (zip 2.8MB, 다운로드 2회), GitHub 이슈 0개
- 분석 방법: 전체 소스 정독 + 데이터 파일 검증. 이 환경은 Linux라 `swift test` 실행과 macOS 실기 확인은 못 했고, 그 부분은 정적 분석으로 표시함. hanja.dat 정렬·이진 탐색 로직은 파이썬 시뮬레이션으로 실측 검증함.
- 규모 실측: Swift 총 4,065줄 — HangulCore 1,090줄 / App 2,625줄 / Tests 338줄 / tools 132줄. hanja.dat 5.4MB·222,657줄, emoji.dat 248KB·4,141줄.

## 한 줄 결론

코어(조합기·규칙)는 테스트까지 갖춘 탄탄한 구조지만, **버그 위험은 전부 App 층의 상태기계와 배포 파이프라인에 몰려 있다.** 최근 커밋 5개 중 3개(영문 칸 판정, 클릭 딜레이, 마지막 글자 사라짐)가 바로 그 층의 수정이었고, 그 층은 테스트가 0개다. 우선순위는 ① 입력 내용 로그 ② 설치 스크립트 무결성 ③ 후보 세션 무효화 ④ 릴리스 서명 일관성 순.

## 1. 구조 개요

| 부분 | 내용 | 평가 |
|---|---|---|
| `Sources/HangulCore/` | 조합기, 자판 4종(390·391·순아래·두벌식), 한자 사전, 한↔영 변환, 단축어, 영문 칸 규칙 | 맥 의존성 없이 분리됨. `swift test` 대상 |
| `App/` | InputMethodKit 본체, 메뉴바, 후보·이모지 창, Caps Lock HID 감시, AX 칸 감시, CGEvent 탭 | 기능 대부분이 여기. 테스트 없음 |
| `build.sh` | `swiftc`로 Core+App 전체를 한 모듈로 일괄 컴파일 | 증분 빌드 없음 (아래 O1) |
| `.github/workflows/release.yml` | 태그 push 때만 테스트·빌드·릴리스 | push/PR CI 없음 (O3) |

잘 된 것 (검증 완료):

- hanja.dat / emoji.dat 키가 바이트 순 정렬 상태이고 중복 키 없음 — 이진 탐색 전제가 실제로 성립함 (전수 검사).
- HanjaDict.lowerBound를 파이썬으로 옮겨 무작위 200개 실존 키 대조 — 전부 정확히 찾음.
- 네트워크 코드 0개 (`URLSession` 등 없음) — README의 "외부 전송 없음"과 일치.
- FieldRules 테스트가 실제 사이트 케이스(네이버·구글 로그인, 카드·인증 칸)로 돼 있고, HangulEngine 테스트는 안드로이드판 회귀를 이식함.
- 클립보드 기록이 Concealed/Transient 타입과 보안 입력 중 복사를 제외함.

## 2. 버그 리포트

### B1. [중간-높음 · 개인정보] 입력한 글자가 시스템 로그에 평문으로 남음

- `App/InputController+Hanja.swift:89` — 커서 앞 글자, `TypedText.text`(최근 입력 최대 64자)를 `privacy: .public` + `info` 레벨로 기록. 같은 파일 58·233줄은 선택 영역·변환 결과를, `InputController+Mistype.swift:38,115`는 선택 영역 전체와 변환 전후 낱말을 같은 방식으로 기록.
- `info` 로그는 macOS 통합 로그에 저장·수집될 수 있어, 비밀번호 칸이 아닌 곳에서 친 계정·주소·대화 내용이 디버깅 정보로 새어 나간다. README의 개인정보 설명("모두 이 맥 안에만") 취지와도 어긋난다.
- 수정: 내용 대신 길이·개수만 남기거나 `.private`로. 키 단위 디버그 로그(`InputController.swift`의 chars 기록)도 동일.

### B2. [중간] 한자·클립보드 후보 창이 열린 뒤 클릭으로 커서가 옮겨가도 세션이 살아 있음

- 세션은 `deactivateServer`에서만 닫히고, `App/main.swift:46`의 전역 마우스 모니터는 `TypedText`만 끊는다.
- 같은 칸 안에서 클릭으로 커서만 옮긴 경우: `HanjaReplace.before(end:)`에 저장된 옛 범위를 교체해 엉뚱한 글자를 바꾸거나, 터미널 경로(`.keystrokes`)는 새 커서 위치에서 후보 키 글자수만큼 Backspace를 흉내 내 지운다.
- 수정: 마우스 클릭 시 한자·이모지 세션도 닫기. 최소한 선택 시점에 저장 범위와 현재 선택 범위가 같은지 재검증.

### B3. [중간 · 배포] install.sh가 다운로드 무결성을 검증하지 않음

- 릴리스 워크플로는 `OGKeyboard.zip.sha256`까지 만들어 올리는데(`release.yml`), `install.sh:23`은 zip만 받아 검증 없이 설치하고 격리 속성까지 해제한다.
- 수정: sha256 파일도 받아 `shasum -a 256 -c` 통과 후에만 설치 진행. 몇 줄이면 된다.

### B4. [낮음-중간] 단축어 `{시간+1}`이 1시간이 아니라 하루를 더함

- `Sources/HangulCore/TextShortcuts.swift:65-77` `shift()`는 단위가 없으면 이름과 무관하게 무조건 일(day) 단위로 더한다. `{날짜+1}`·`{요일+1}`은 맞지만 `{시간+1}`은 날짜만 하루 가고 표시 시각이 그대로라 사실상 무동작. 관련 테스트도 없다.
- 수정: 토큰 이름별 기본 단위 분기(시간 → hour), 또는 시간 토큰의 증감 미지원을 명시하고 정규식에서 제외.

### B5. [낮음] FieldWatcher의 pid 캐시가 재사용된 pid에서 오작동

- `App/FieldWatcher.swift:29,57-58` `manualEnabled: Set<pid_t>`에 넣기만 하고 앱 종료 시 제거하지 않는다. 종료한 Chromium의 pid를 새 Chromium 프로세스가 재사용하면 `AXManualAccessibility`를 다시 켜지 않아 그 프로세스에서는 자동 영문이 동작하지 않는다 (입력기 재시작 전까지). 집합 자체도 무한히 자란다(크기는 미미).
- 수정: `didTerminateApplication`에서 제거하거나, watch 때마다 속성을 확인해 필요하면 다시 설정.

### B6. [낮음 · 개인정보] 클립보드 보관 기간이 지나도 저장소에서 안 지워짐

- `App/ClipboardHistory.swift:33-38` `clips` getter는 걸러서 보여주기만 하고, 실제 삭제는 다음 복사가 일어나 `poll()`이 저장할 때만 일어난다. 보관 시간을 짧게 했다가 "계속"으로 되돌리면 만료됐던 항목이 되살아난다.
- 수정: 보관 시간 변경 시점과 앱 시작 시점에 한 번 정리해 다시 저장.

### B7. [낮음] 바로잡기 연속 상태(MistypeChain)가 앱 전환에도 유지됨

- `App/InputController+Mistype.swift:5-13`의 정적 상태가 `activateServer`에서도 초기화되지 않는다. 2초 안에 다른 앱으로 가서 바로잡기를 하면, 그 앱 글자 끝이 이전 앱의 변환 결과와 우연히 같을 때 이전 방향·연속 횟수로 동작한다.
- 수정: 체인에 번들 ID를 포함하거나 활성화 시점에 리셋.

### B8. [낮음 · 빌드] 앱 버전 문자열이 태그와 자동으로 안 맞음

- `App/Info.plist`의 `CFBundleShortVersionString`은 수동 값("0.4")이고, `build.sh`는 `CFBundleVersion`(커밋 수)만 주입한다. 지금까지는 릴리스 커밋마다 plist를 손으로 올렸지만(0.1→0.4 히스토리 확인), 한 번 빠뜨리면 태그는 v0.5.0인데 정보 창·설치 안내에는 0.4로 찍힌다.
- 수정: 릴리스 워크플로에서 태그 값을 plist에 주입.

### B9. [낮음 · 검증 공백] 순아래 자판과 순서 입력 경로가 사실상 미검증

- `HangulEngine.inputSequential`(모아치기 끈 경로)은 앱 어디에서도 켤 수 없다 — `moachigi`를 바꾸는 코드가 없어 사실상 dead path이고, 설정으로 노출할지 제거할지 결정이 필요하다.
- 순아래(3s) 자판은 타이핑 테스트가 없고 "모든 키가 0이 아님" 검사만 있다. 390·391·두벌식과 같은 수준의 회귀 케이스 추가 권장.

### B10. [잠재] FieldRules 오탐 여지

- 제외어(검색·메시지 등) 검사는 칸 이름·설명·placeholder만 보고, `domIdentifier` 토큰 검사는 그 뒤에 별도로 돈다. 제외어가 라벨에 없는 칸(예: 라벨 "받는 사람" + id `user_id`)은 토큰 `id` 하나로 영문 전환될 수 있다.
- `phrases`의 "홈페이지", 토큰의 `date`·`code`·`number`·`cc`처럼 넓은 항목도 한국어 입력이 정상인 칸에서 걸릴 여지가 있다. 실측 케이스를 테스트에 계속 추가하는 지금 방식이 맞고, 오탐 제보용으로 판정 근거(어느 규칙에 걸렸는지)를 로그에 남기면 대응이 빨라진다.

### B11. [잠재] 화면이 없을 때 강제 접근

- `CandidatePanel.swift`와 `EmojiPanel.swift`의 `origin()`이 `NSScreen.screens[0]`을 강제 인덱싱한다. `ModeIndicator`는 같은 상황에서 guard로 빠져나간다. 디스플레이가 전혀 없는 실행은 드물어 잠재로 분류하되, guard로 통일하는 게 안전하다.

## 3. 최적화 방안

### O1. [높음 · 구조] App을 빌드 가능한 타깃으로 — 증분 빌드와 테스트의 전제

- 현재 `build.sh`는 매번 전체를 `swiftc` 한 번으로 컴파일한다 (증분 없음). 4천 줄에선 버틸 만하지만 파일이 늘수록 그대로 느려진다.
- 더 본질적인 문제: HangulCore에서 `public`인 건 `FieldRules`뿐이고 나머지는 전부 internal이다. 지금 앱이 되는 건 Core와 App을 한 모듈로 합쳐 컴파일하기 때문이라, 모듈을 나누는 순간 깨진다.
- 방안: HangulCore 핵심 타입을 public으로 열고 App을 SwiftPM 실행 타깃(또는 Xcode 프로젝트)으로 만들면 증분 빌드, App 층 테스트, 정적 분석이 한 번에 풀린다. oasis-reader에서의 대형 파일 분리와 달리, 여기는 규모가 작아 지금 하는 게 싸다.

### O2. [높음 · 배포] 릴리스 서명을 일관되게 — 업데이트마다 권한이 풀리는 문제

- CI에는 서명 인증서가 없어 릴리스가 임시(ad-hoc) 서명으로 나간다. 그래서 버전이 바뀔 때마다 macOS가 다른 앱으로 보고 손쉬운 사용·입력 모니터링 권한이 풀린다 (README가 사용자에게 재등록을 안내 중).
- 공증(Developer ID)까지 안 가도, 자체 서명 인증서 하나를 CI 시크릿에 넣어 릴리스에 쓰면 서명 식별자가 안정돼 권한이 유지된다. 사용자 마찰이 가장 큰 지점이라 효과 대비 비용이 제일 좋다.

### O3. [중간 · CI] push/PR에도 테스트를

- 지금은 태그를 올려야만 `swift test`가 돈다. `macos-15`에서 `swift test`만 도는 가벼운 워크플로를 push/PR에 걸면 깨진 main을 릴리스 직전이 아니라 커밋 시점에 잡는다.

### O4. [중간 · 성능] HanjaDict가 메모리 매핑을 스스로 무효화

- `Sources/HangulCore/HanjaDict.swift:25-26` — `.mappedIfSafe`로 읽은 Data를 `[UInt8](data)`로 통째 복사해 hanja 기준 5.4MB 힙 복사가 생긴다. 주석의 "메모리 매핑" 설명과 실제가 다르다.
- 방안: Data를 그대로 들고 바이트 subscript로 접근하거나, 줄 시작 오프셋 인덱스를 한 번 구축해 두면 복사 제거 + 조회도 빨라진다. 단, 사전은 첫 한자 호출 때만 lazy하게 올라가 체감 지연은 작으니, 프로파일에서 확인 후 순위를 정할 것.

### O5. [중간 · 성능] 이모지·후보 창이 키 입력마다 전체를 다시 그림

- `EmojiPanel.show`는 방향키 한 번에도 탭+40개 셀 전체를 새로 만들고, `CandidatePanel.show`도 행 전체를 재생성한다. 방향키를 누르고 있으면(키 반복) 그대로 반복된다.
- 방안: 셀을 재사용하고 선택 하이라이트와 이름 줄만 갱신.

### O6. [중간 · 반응성] FieldWatcher 판정 큐 적체

- 칸 하나에 AX 속성 조회가 최대 8회, 각 0.25초 타임아웃이라 무응답 앱에서는 직렬 큐(`FieldWatcher.swift:34`)가 밀리고 뒤 칸 판정이 늦게 도착할 수 있다. 순서 자체는 큐 순서대로 보장되지만 지연이 쌓인다.
- 방안: 큐에 들어간 판정 중 최신 요소만 남기고 중간 것은 버리기(coalescing), 또는 세대 번호를 붙여 오래된 판정은 apply에서 버리기. 최근 커밋(5516b14)이 클릭 딜레이를 같은 이유로 고친 전례가 있다.

### O7. [낮음] 그 밖의 정리

- 클립보드 폴링 0.5초(`ClipboardHistory.swift:40`) — pasteboard 변경 알림 API가 없어 폴링 자체는 표준이지만, 1초로 늦춰도 체감이 없고 깨우기가 절반이 된다.
- `TextShortcuts.format()`이 토큰마다 `DateFormatter`를 새로 만든다 — 정적 캐시로. 사용 빈도가 낮아 체감은 미미, 코드 정리 수준.
- UserDefaults 키 문자열이 8개 파일에 흩어져 있다 — 키 상수 한 곳으로 모으면 오타형 버그를 막는다.

### O8. [중간 · 구조] 상태기계를 테스트 가능한 형태로

- 최근 수정이 몰린 곳(FieldWatcher의 전환/복귀, MistypeChain, ModeState의 앱별 기억)이 전부 전역 정적 상태라 테스트를 붙일 수 없고, B5·B7 같은 누수가 여기서 나왔다.
- 방안: 판정 로직 자체는 이미 순수한 `FieldRules`로 잘 빠져 있다. 다음 한 걸음으로 "판정 결과 → 한/영 전이" 부분만 순수 구조체로 빼 HangulCore에서 테스트하면, 회귀가 가장 잦은 지점을 커버할 수 있다.

## 4. 우선순위 로드맵

| 단계 | 항목 | 이유 |
|---|---|---|
| 0단계 (바로) | B1 로그 정리, B3 sha256 검증, B2 클릭 시 세션 닫기, O3 push CI | 전부 작고, 개인정보·무결성·오작동에 직결 |
